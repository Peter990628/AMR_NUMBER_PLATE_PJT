# 4단계 후보의 시간 일관성 확인

관측 후보가 한 프레임에서 크게 달라졌을 때 바로 채택하지 않고, 같은 고정 좌표계에서 연속 관측의 일관성을 확인한다. 원본 측정값은 별도 토픽에 그대로 남긴다. 확인된 출력도 현재 관측의 기하를 사용하며 평균값이나 마지막 유효 후보로 대체하지 않는다.

## 도입 배경과 확인 범위

2026-11-12의 −10° 정지 시험에서는 후보 A의 평균 대비 위치 편차가 한 프레임에서 44.42cm였고, 앞뒤 프레임과의 거리는 약 46.6cm였다. 해당 관측 끝점도 함께 움직였다. 당시 기록만으로는 클러스터 선택, 직선 적합, 끝점 산출 중 어느 부분이 원인인지 확정할 수 없었다. 자세한 수치는 [회전 검증 기록](stage4_rotation_check.md)에 있다.

안정화 적용 전 추가로 수집한 30초 기록에서는 원본 스캔·측면 추정·후보의 시각이 일치하는 89쌍을 확보했다. 원본 후보 중 87개가 유효했고, 인접 유효 샘플 사이의 최대 위치 변화는 후보 약 18.09cm, 측면 관측 끝점 약 17.91cm였다. 이 구간에서는 앞선 46.6cm 사례가 재현되지 않았다. 최대 변화 전후의 스캔을 적합 직선과 비교하면 끝점 빔이 1174에서 1204로 바뀌었다. 빔 1204의 직선까지 거리가 56.2mm에서 27.0mm로 줄면서 30mm inlier 기준 안에 들어왔고, 선분 길이는 3.454m에서 3.639m로 늘었다. 관측 끝점 변화가 후보 변화로 전달됐다는 증거이며, 센서 잡음·차체 형상·직선 적합 각각의 기여를 확정한 것은 아니다.

추가 원본 기록에서는 한 스캔의 중앙 빔 535~1067이 모두 `-1`이 됐다. 유효 입력은 578→197→577점, 선택 선분 길이는 3.582→1.000→3.560m로 변했다. 50점·147점으로 나뉜 두 클러스터 중 끝부분의 147점에서 137개 inlier를 선택하면서 후보가 약 3m 이동했다. 이때 로봇 이동은 약 3.5~3.8µm이고 법선 반전도 없었다. 스캔 일부 소실과 짧은 관측 구간의 선택은 확인했지만, 소실의 근본 원인은 미확정이다. 이 원본 전용 기록은 `shadow/fragment_diagnostics.json`에 정리했다. 해당 수집 때 비교용 필터 기동 확인이 실패했으므로 실시간 필터 출력은 없다.

이 기능은 **관측 후보의 채택 조건**이다. 차량 앞뒤 식별, 실제 범퍼 위치 추정, 충돌 여유, 이동 경로, `base_link` 주행 목표 생성은 수행하지 않는다. 확인된 후보에도 허용 범위 안의 측정 흔들림이 남는다.

## 토픽과 출력 계약

```text
/vehicle_side/estimate
        ↓ 기하 후보 생성
/observation_candidates/raw
        ↓ 관측 시각의 TF + 연속 관측 확인
/observation_candidates
```

| 토픽 | 내용 |
|---|---|
| `/observation_candidates/raw` | 원본 측면 추정으로 계산한 현재 후보. 확인 전 결과와 무효 상태를 포함한다. |
| `/observation_candidates` | 시간 일관성을 확인한 후보 또는 명시적인 무효 상태. 후속 노드는 이 토픽의 `valid`를 검사한다. |
| `/debug/observation_candidates/raw` | 원본 후보의 RViz 마커. |
| `/debug/observation_candidates` | 확인된 후보의 RViz 마커. 무효화되면 삭제한다. |

확인된 메시지의 `header.stamp`, `header.frame_id`, `viewpoints`, `look_at`, 생성 거리 설정은 **채택된 현재 원본 메시지와 같다**. 기본 출력 좌표계는 `observation_lidar`이며, 방향도 이 좌표계의 현재 후보 방향이다. 상태 문자열만 `stable_candidates`로 바뀐다. 비교에 `odom`을 사용한다고 해서 출력 메시지의 좌표계를 `odom`으로 바꾸지는 않는다.

무효 출력은 `valid: false`이고 `viewpoints`와 `look_at`이 비어 있다. 직전 유효 후보를 다시 발행해 유효한 관측처럼 유지하지 않는다.

## 확인 방법

1. 원본 후보의 획득 시각으로 `odom ← observation_lidar` TF를 조회한다. 최신 TF로 대신 계산하지 않는다.
2. 두 후보 위치와 두 `look_at` 끝점을 회전·이동을 모두 적용해 `odom`으로 변환한다. 위치 비교는 XYZ 전체의 3차원 거리로 한다. 방향은 변환된 자세의 yaw를 사용한다.
3. 후보 A/B의 이름에 의존하지 않고, 위치의 기하학적 대응으로 두 후보를 맞춘다. 방향 차이는 ±π 경계를 감안해 계산한다.
4. 새 관측을 보관 중인 최근 최대 3개 관측 각각과 비교한다. 후보 위치와 관측 끝점 모두 15cm 이내이고 yaw 차이가 3° 이내여야 한다. 인접한 두 관측만 비교하지 않는다.
5. 연속 3개 관측이 조건을 만족하면 현재 원본 후보를 채택한다. 이후에도 새 관측을 보관된 관측 전체와 비교하고, 보관 개수는 최대 3개로 유지한다.

조건을 벗어난 관측이 들어오면 즉시 무효화하고, 그 관측부터 새로운 확인 구간을 시작한다. 따라서 한 프레임의 점프 뒤 원래 위치로 돌아와도 돌아온 위치에서 다시 3개가 일치해야 한다. 반대로 실제로 관측 형상이 달라진 상태가 3개 이상 일관되게 유지되면 새 위치를 채택할 수 있다.

| 설정 | 기본값 | 의미 |
|---|---:|---|
| `confirmation_count` | 3 | 채택에 필요한 연속 확인 수. 허용 범위 2~20. |
| `max_position_delta_m` | 0.15m | 후보 위치와 관측 끝점 각각의 최대 3차원 차이. |
| `max_yaw_delta_deg` | 3° | 고정 좌표계에서 후보 방향의 최대 차이. |
| `max_source_gap_sec` | 0.35초 | 연속 확인을 유지할 수 있는 원본 획득 시각 간격. |
| `tf_wait_timeout_sec` | 0.2초 | 정확한 관측 시각의 TF를 기다리는 최대 실제 시간. |
| `max_input_age_sec` | 0.5초 | 시뮬레이션 현재 시각에 비해 허용하는 입력의 최대 나이. |
| `future_tolerance_sec` | 0.1초 | 시뮬레이션 현재 시각보다 앞선 입력의 허용 범위. |
| `input_timeout_sec` | 1.0초 | 새 원본 메시지가 없을 때 무효화하는 실제 시간. |

설정 파일은 `config/candidate_stability.yaml`이다. 노드 설정은 실행 시 읽으며 실행 중 변경을 허용하지 않는다. 원본 메시지의 `extension_m` 또는 `standoff_m`이 달라지면 이전 확인 상태와 마커를 즉시 무효화하고 새 설정으로 다시 확인한다.

## 무효화와 복구

| 상황 | 처리 |
|---|---|
| 확인 수가 아직 부족함 | `confirming:1/3`, `confirming:2/3`; 후보를 발행하지 않는다. |
| 위치·끝점·방향 급변 | `unstable:1/3`; 현재 관측부터 확인을 다시 시작한다. |
| 원본 측면 추정 또는 후보가 무효 | 확인 구간과 TF 대기열을 즉시 비우고 마커를 삭제한다. |
| TF가 늦게 도착함 | 정확한 시각의 TF를 최대 0.2초 기다린다. 제한 안에 도착하면 해당 시각으로 처리한다. |
| TF 대기 제한 초과 | `tf_unavailable`; 대기 관측을 버리고 다시 확인해야 한다. 늦은 TF만으로 이전 후보를 되살리지 않는다. |
| 입력이 오래됐거나 너무 미래임 | `stale_input` 또는 `future_input`; 확인 상태를 초기화한다. |
| 같은 원본 시각 반복 또는 시각 역행 | `duplicate_stamp` 또는 `time_reset`; 기존 확인 구간을 이어 쓰지 않는다. |
| 입력 중단 또는 Pause | 실제 시간 1초를 넘기면 `input_timeout`. 시뮬레이션 시각이 멈춰도 동작한다. |
| 정상 입력 재개 | 새로운 연속 관측 3개를 확인한 뒤 다시 유효해진다. |

TF가 잠시 늦는 경우에는 위 대기 제한 안에서 처리를 기다릴 수 있다. 무효 상태가 확정되면 마지막 유효 기하를 대체 출력으로 사용하지 않는다. 시뮬레이션 시각이 뒤로 돌아가도 기존 확인 구간을 초기화한다.

원본이 자주 무효가 되거나 끝점이 자주 달라지면 확인된 후보가 없는 구간이 늘어날 수 있다. 이는 원본 품질 문제를 숨기지 않는 동작이며, 모든 프레임을 유효하게 만드는 기능은 아니다. 허용 오차를 늘리는 대신 원본 상태와 끝점 변동을 함께 확인한다.

## 실행과 RViz 확인

빌드 후 새 터미널에서 실행한다. 이미 실행 중인 같은 후보 파이프라인을 중복으로 띄우지 않는다. 이전 버전의 후보 노드가 실행 중이면 그 실행을 종료한 뒤 새 launch를 시작한다.

```bash
cd ~/peter_pjt/ros2_ws
source /opt/ros/humble/setup.bash
source install/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOG_DIR=/tmp/amr_candidate_stability_ros_logs

ros2 launch amr_reobservation observation_candidates.launch.py
```

이 launch는 측면 추정, 원본 후보 생성, 후보 확인 노드와 RViz를 함께 실행한다. 측면 추정 노드만 별도로 실행 중이면 `start_estimator:=false`를 붙인다. RViz 없이 실행하려면 `rviz:=false`를 사용한다.

RViz는 기본적으로 확인된 후보를 표시한다. 원본 후보 표시 항목은 기본값이 꺼져 있으므로 비교할 때만 켠다. 원본 마커만 켜 두면 확인 단계에서 걸러낸 점프도 그대로 보인다. 상태를 직접 확인하려면 다음 명령을 사용할 수 있다.

```bash
ros2 topic echo /observation_candidates --once
ros2 topic echo /observation_candidates/raw --once
```

## 원본과 확인 결과를 같은 시각으로 기록

프로젝트 루트의 `tools/record_candidate_stability.py`는 스캔·측면 추정·원본 후보·확인 결과와 [적합 진단](fit_diagnostics.md)을 구독한다. 로봇 명령이나 TF를 발행하지 않는다. 후보와 끝점은 원본 stamp의 TF로 변환하고, 같은 epoch·원본 좌표계·stamp끼리 대응시킨다. 진단은 TF 없이 저장하고 같은 기준으로 대응한다.

새 launch를 적용한 뒤의 수집 명령은 다음과 같다. 수집하는 30초 동안 AMR과 차량을 정지시킨 채 Play를 유지한다.

```bash
cd ~/peter_pjt
source /opt/ros/humble/setup.bash
source ros2_ws/install/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOG_DIR=/tmp/amr_candidate_stability_record_logs

python3 tools/record_candidate_stability.py \
  --duration 30 \
  --raw-topic /observation_candidates/raw \
  --stable-topic /observation_candidates \
  --output-dir local_artifacts/candidate_stability_2026-11-12/after_next
```

적용 전 구성을 다시 측정해야 한다면, 이전 구성에서는 원본이 `/observation_candidates`에 발행된다는 점을 반영한다. 다음 명령은 **안정화 적용 전 파이프라인을 위한 기록 예시**이며 현재 launch의 전후 비교에는 위 명령을 쓴다.

```bash
python3 tools/record_candidate_stability.py \
  --duration 30 \
  --raw-topic /observation_candidates \
  --stable-topic /observation_candidates/stable \
  --output-dir local_artifacts/candidate_stability_2026-11-12/before_next
```

출력 폴더에는 다음 파일을 저장한다. 이미 같은 이름의 결과 파일이 있으면 덮어쓰지 않으므로 재수집할 때에는 새 폴더명을 사용한다. `local_artifacts/`는 Git에서 제외된다.

- `streams.jsonl`: 무효와 미대응 메시지를 포함한 수신 기록. 스캔의 원본 거리 배열도 보관한다.
- `transformed.jsonl`: 원본 시각의 TF와 고정 좌표계 변환 결과. TF가 없는 관측은 그 사실을 남긴다.
- `paired.jsonl`: 같은 시각의 측면 추정·후보·확인 결과와 스캔 기록 번호를 연결한 데이터.
- `report.json`: 유효 비율, 상태별 개수, 적합 지표, 후보와 끝점의 변화량 요약.

같은 source stamp에 유효 출력 뒤 watchdog 무효 출력이 올 수 있으므로, 대응 기록의 `stable`에는 모든 도착 메시지를 보관하고 `stable_latest`에는 최종 상태를 남긴다. 단순 발행 메시지의 유효 비율과 각 source sample의 최종 유효 비율도 구분한다.

변화량 표는 연속한 **유효** 관측끼리 비교한다. 중간에 무효 구간이 있으면 시간 간격이 길어질 수 있고, 새 위치를 재확인한 뒤에는 두 유효 관측 사이의 차이가 15cm를 넘을 수도 있다. `dt_sec`, 중간 상태, 재확인 구간을 함께 확인해야 한다. 허용 범위 안의 흔들림까지 평균 처리해서 없앤 결과로 해석하지 않는다.

## 자동 검증과 실제 수집 결과

ROS와 독립된 C++ 단위 테스트 16개에서 44cm 단일 프레임 점프, 복구 확인 수, 지속적인 새 위치, A/B 교환, 고정 좌표계 회전, ±π 경계, 끝점·높이 변화, 시간 간격, 시각 중복·역행, 잘못된 값과 설정을 검사한다. 인접 비교만 하면 놓치는 누적 변동도 검사한다.

전체 C++ GTest 75개(기존 59개 + 확인 로직 16개)와 기록 도구의 오프라인 테스트 9개가 통과했다. 별도 ROS smoke는 도메인 88의 전용 토픽에서 50개 검사를 통과했다. 원본 시각의 TF, 지연 TF, 오래된 TF로 대체하지 않는 동작, 급변 차단과 복구, 무효 입력, Pause 타임아웃, 시각 초기화와 설정 변경 즉시 무효화를 실제 노드에서 확인한다. 최종 설치본은 TF 전용 스레드 오류 로그도 0건이다. 조회는 nonblocking BufferCore 호출을 사용하고 wall timer에서 재시도한다.

```bash
cd ~/peter_pjt/ros2_ws
source /opt/ros/humble/setup.bash
source install/setup.bash
```

### +10° 기록의 무효 판정 원인 재현

위 91개 원본 스캔을 실제 C++ 전처리기와 진단 출력을 추가한 측면 추정 코드의 임시 복사본으로 재생했다. 실행 중인 노드·설정·생산 소스는 변경하지 않았다. 기본 설정으로 79개 유효·12개 `no_valid_line`, 전처리 점 수·클러스터 수가 실시간 기록과 모두 일치했고 기존 유효 프레임의 길이·RMSE도 정확히 재현됐다.

진단용 복사본의 반복 상한만 30회로 바꿔 같은 입력을 재생한 결과:
